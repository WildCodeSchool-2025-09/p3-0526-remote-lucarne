## 1. Diagnostic et périmètre

Le projet possède une base technique cohérente : domaines identifiables, contrats Zod partagés, autorisations serveur, transactions et contraintes PostgreSQL pour les invariants critiques. Les tests couvrent plusieurs véritables comportements métier, y compris les écritures concurrentes et les refus atomiques. La principale faiblesse immédiate est la reproductibilité de la validation : le build Web échoue, la préparation de la CI échoue sur une base vierge et des images nécessaires au build ne sont pas suivies par Git.

L'audit porte sur **l'état de travail local**, et non seulement sur HEAD. Un chantier important était déjà présent, avec de nombreux fichiers modifiés et des fonctionnalités non suivies par Git. Aucun reset, checkout, staging, commit, seed ou migration de la base de développement n'a été effectué. Une photographie des 458 fichiers de sources, base et tests a été conservée avant les modifications de cette passe ; 17 fichiers ont changé, 441 sont restés identiques et aucun n'a été supprimé.

L'audit n'est pas exhaustif. Il combine lecture détaillée des parcours ci-dessous, recherches transversales, vérifications statiques et exécution des suites existantes. Les résultats de tests ne constituent pas un pourcentage de couverture.

## 2. Problèmes prioritaires

Gravité : **élevée** = validation bloquée ou risque sérieux sur une frontière publique ; **moyenne** = comportement incorrect sur un cas identifiable ou défaut de maintenance important ; **faible** = observabilité/documentation. Une propriété du code peut être démontrée alors que sa manifestation en production reste un risque à vérifier.

### F01 — Élevée, défaut démontré : compilation Web bloquée

- Fichiers : [CreatePlayerForm.tsx](apps/web/src/features/player/components/CreatePlayerForm.tsx), ligne 132 ; [UpdatePlayerForm.tsx](apps/web/src/features/player/components/UpdatePlayerForm.tsx), ligne 147 ; [playerStyles.ts](apps/web/src/features/player/playerStyles.ts), ligne 1.
- Preuve : les formulaires accèdent à `playerStyles.formLayout`, absent de l'objet. TypeScript produit deux TS2339 ; ESLint produit deux `no-unsafe-assignment`. Même résultat avant et après cette passe.
- Impact : `check-types`, `build`, `check` et donc `validate` ne peuvent pas réussir intégralement. Vitest passe malgré ce défaut car sa transformation n'est pas un contrôle des types.
- Recommandation : définir la disposition attendue du formulaire puis restaurer la propriété ou choisir explicitement une propriété existante compatible. Faire types, lint, build et contrôle visuel des deux formulaires. Coût faible ; risque visuel si la classe est choisie arbitrairement.
- Non corrigé : ajouter/changer une classe modifie le rendu et dépasse la passe de présentation du code demandée.

### F02 — Élevée, défaut reproduit : la CI s'arrête avant les migrations

- Fichier : [.github/workflows/check.yml](.github/workflows/check.yml), lignes 46 et 47.
- Preuve : le job lance `prisma migrate status` avant `prisma migrate deploy` sur son PostgreSQL éphémère. Sur une nouvelle base temporaire, le premier status a renvoyé **1**, avec 14 migrations en attente. Après deploy : deploy **0**, status **0**, diff avec le schéma **0**.
- Impact : le bloc shell GitHub s'arrête avant deploy ; les contrôles et le déploiement conditionné au succès de CI restent bloqués, même une fois F01 corrigé.
- Recommandation : appliquer les migrations sur la base éphémère, puis contrôler status et diff. Coût faible ; conserver le refus des migrations échouées et de la dérive du schéma.
- Déjà signalé dans le README ; confirmé par exécution pendant cet audit. Workflow conservé dans cette passe.

### F03 — Élevée, défaut de reproductibilité démontré : logos absents d'un clone

- Fichiers : [DashboardSidebar.tsx](apps/web/src/components/dashboard/DashboardSidebar.tsx), lignes 2–3 ; [DashboardMobileHeader.tsx](apps/web/src/components/dashboard/DashboardMobileHeader.tsx), ligne 3 ; [.gitignore](.gitignore), règle `/apps/web/docs/`.
- Preuve : imports statiques de deux PNG sous `apps/web/docs/images` ; `git ls-files apps/web/docs/images` ne retourne aucun fichier ; `git check-ignore` confirme leur exclusion. Ils existent localement et Vite les incorpore au bundle.
- Impact : le succès d'un bundle dans cet espace de travail ne prouve pas qu'un clone ou un conteneur de CI dispose des ressources nécessaires.
- Recommandation : faire une exception d'ignore pour ces assets, ou décider d'un emplacement d'assets suivis puis adapter les imports. Coût faible ; vérifier provenance/licence et clone propre. Aucun déplacement appliqué.

### F04 — Élevée comme risque de disponibilité, cause démontrée : limiteur non borné

- Fichier : [loginRateLimit.ts](apps/api/src/middlewares/loginRateLimit.ts), lignes 10, 28 et 47 ; [auth.routes.ts](apps/api/src/features/auth/auth.routes.ts), ligne 13.
- Preuve : une Map globale conserve chaque couple IP/email. L'expiration remet à zéro une clé revisitée, mais ne retire pas les anciennes clés. `clearLoginRateLimit` n'est pas une purge périodique de production. Le limiteur s'exécute avant la validation du login ; des emails différents, même invalides, alimentent donc cette Map.
- Impact : croissance mémoire liée au nombre de clés distinctes ; changer d'email contourne une limite portée uniquement par ce couple. Aucun épuisement mémoire sous charge n'a été tenté.
- Recommandation : ajouter une limite de capacité et une éviction des entrées expirées ; définir aussi une protection par IP et vérifier le comportement derrière Traefik. Si plusieurs instances sont réellement prévues, évaluer un compteur partagé. Coût faible à moyen ; risque de bloquer des utilisateurs légitimes si les seuils ou les proxys de confiance sont mal choisis.

### F05 — Moyenne, incompatibilité de configuration démontrée : images externes et CSP

- Fichier : [app.ts](apps/api/src/app.ts), ligne 14 ; contrats `pictureUrl`/`logoUrl` dans Shared ; production servie par Express dans ce même fichier.
- Preuve : `helmet()` utilise les directives par défaut du paquet installé. La lecture de `helmet.contentSecurityPolicy.getDefaultDirectives()['img-src']` retourne `["'self'", "data:"]`. Les contrats et formulaires permettent pourtant des URLs d'images externes.
- Impact : une image HTTP(S) d'une autre origine acceptée par l'API sera bloquée par la politique CSP lorsque l'interface est servie par Express en production. Le serveur Vite de développement ne reproduit pas cette frontière. Pas de reproduction visuelle navigateur réalisée.
- Recommandation : décider des origines d'images autorisées, les aligner avec la validation et la CSP, puis tester une vraie réponse de production en navigateur. Coût faible à moyen ; éviter d'élargir toutes les directives CSP pour résoudre seulement les images.

### F06 — Moyenne, état de cache reproduit : changement de token sans purge

- Fichiers : [authToken.ts](apps/web/src/lib/authToken.ts), lignes 9–10 ; [auth.service.ts](apps/web/src/services/auth.service.ts), appel `setAccessToken` ; [DevLoginPage.tsx](apps/web/src/pages/dev/DevLoginPage.tsx), session invalide permettant une reconnexion.
- Preuve : un diagnostic sur le module réel transpilé, avec sessionStorage simulé et un véritable QueryClient, stocke un token A, une donnée du compte A, puis remplace le token par B. La donnée A reste dans le cache ; `clearAccessToken()` l'efface. Les clés de requêtes ne portent pas l'identité du compte.
- Impact : une reconnexion avec un token expiré encore stocké, sans logout ni réponse 401 préalable, peut réutiliser des données fraîches de l'ancienne session. Cela concerne l'affichage et le cache ; aucune possibilité d'écriture non autorisée côté serveur n'a été démontrée.
- Recommandation : définir explicitement la transition de session et purger les données/in-flight queries concernées lors du remplacement de l'identité. Tester A → expiration locale → connexion B, ainsi qu'une ancienne réponse reçue après la nouvelle connexion. Coût faible à moyen ; préserver la protection déjà existante contre les 401 tardifs d'anciennes sessions.

### F07 — Moyenne, traduction d'erreur démontrée : conflit Serializable Season devient 500

- Fichiers : [season.repository.ts](apps/api/src/features/season/season.repository.ts), transaction `updateSeasonOptimistic`, ligne 100 ; [season.service.ts](apps/api/src/features/season/season.service.ts), lignes 82 et 113 ; [mapErrorToAppError.ts](apps/api/src/errors/mapErrorToAppError.ts), ligne 11 ; [errorHandler.ts](apps/api/src/middlewares/errorHandler.ts), ligne 47.
- Preuve : `updateSeasonService` traduit P2002, mais laisse P2034 remonter. Le mapper global ne traduit pas P2034. Un diagnostic avec repository simulé injectant P2034 a confirmé que le service laisse l'erreur inchangée et que le mapper retourne `null` ; le handler produit alors 500.
- Impact : en cas d'échec de sérialisation, l'utilisateur obtient une erreur serveur générique au lieu d'un conflit récupérable. Le test existant de version obsolète est séquentiel et passe ; il ne démontre pas la gestion d'un conflit réellement simultané. Aucun conflit Season réel n'a été forcé pendant cette passe.
- Recommandation : traiter les erreurs de concurrence à la frontière métier de cette mutation, à l'image de MATCH, puis ajouter un test simultané donnant un succès et un conflit sans écrasement. Coût faible à moyen ; ne pas relancer automatiquement une écriture avec des valeurs devenues obsolètes.

### F08 — Moyenne, requêtes incohérentes démontrées : compteurs de matchs supprimés

- Fichiers : [participation.repository.ts](apps/api/src/features/participation/participation.repository.ts), ligne 9 ; [season.repository.ts](apps/api/src/features/season/season.repository.ts), ligne 143 ; suppression dans [match.service.ts](apps/api/src/features/match/match.service.ts).
- Preuve : les deux calculs de `scheduledMatchCount` filtrent `status: 'SCHEDULED'` sans `isActive: true`. La suppression d'un match fixe seulement `isActive: false` et conserve son statut. Les listes MATCH excluent, elles, les inactifs.
- Impact : un match à venir supprimé continue à contribuer au compteur et à la prévisualisation de retrait d'une participation. Le compteur peut annoncer un match que le calendrier courant ne montre plus.
- Recommandation : confirmer que ce compteur décrit les rencontres courantes plutôt que les archives, puis ajouter le filtre cohérent dans les deux chemins. Tester créer → affecter → supprimer → détail saison/prévisualisation. Coût faible ; conserver les archives et les contraintes de préservation de l'historique. Aucun compteur corrigé dans cette passe.

### F09 — Faible, défaut d'observabilité démontré : logs sans statut métier

- Fichier : [errorHandler.ts](apps/api/src/middlewares/errorHandler.ts), lignes 8–20 ; [AppError.ts](apps/api/src/errors/AppError.ts).
- Preuve : le log lit `error.status`, mais AppError expose `statusCode`. Le champ nommé `code` contient `error.name`, pas le code applicatif. Le mapping est effectué après l'écriture du log.
- Impact : les erreurs métier peuvent être journalisées sans statut HTTP et avec le nom générique AppError, ce qui limite le diagnostic des 403/409/500. La réponse HTTP utilise bien le statut et code applicatifs.
- Recommandation : journaliser après classification avec statut/code sûrs, et conserver les détails techniques sensibles hors du payload client. Coût faible ; tester qu'aucun secret, SQL ou corps de requête n'est enregistré.

### F10 — Faible à moyenne, documentation incohérente démontrée

- Fichiers : [README.md](README.md), lignes 18, 59–61 et section « limitations confirmées » ; [ARCHITECTURE.md](docs/ARCHITECTURE.md), ligne 50 ; [DATA_MODEL.md](apps/api/docs/DATA_MODEL.md), passages MATCH encore formulés au futur.
- Preuve : le README décrit encore l'absence de parcours saison/participation/match ; le routeur monte ces fonctionnalités. Il annonce UTC et clôture lors de désactivation de toute personne, alors que `assignmentDate` utilise Paris et que la désactivation d'une joueuse conserve les dates. L'architecture commune annonce l'absence de portail métier public, alors que `/matches` existe. Certaines limitations du README décrivent des comportements déjà modifiés.
- Impact : un contributeur peut réintroduire un ancien modèle ou chercher une fonctionnalité déjà disponible. Les documents locaux sous `docs` et les AGENTS sont largement ignorés par Git ; la transmission des conventions à un clone doit aussi être vérifiée.
- Recommandation : distinguer explicitement l'historique des fiches et l'état actuel ; conserver les décisions déjà validées. Coût faible à moyen ; ne pas effacer les questions ouvertes en les présentant comme arbitrées. Documents existants conservés dans cette passe ; ce rapport décrit l'état observé.

| Sujet | Preuve locale | Limite et vérification proposée |
| --- | --- | --- |
| Métadonnées Prisma d'exclusion | Le mapper reconnaît `meta.code = '23P01'`, mais pas cette valeur sous `driverAdapterError.cause.code`, contrairement aux SQLSTATE MATCH ; le diagnostic injecté de cette forme retourne null | Les tests PostgreSQL actuels passent. Capturer le format réel dans chaque chemin Prisma utilisé avant de conclure à une régression de production ; ajouter un test ciblé de la forme imbriquée si elle est pertinente |

| Génération de calendrier | Quantités jusqu'à INTEGER max ; produit généré en SQL avec timeout local 4 s, route ADMIN | La limite technique évite le tableau N×M côté Node et assure le rollback. Mesurer la contention et convenir d'une borne opérationnelle si le besoin réel l'exige |
| Stockage des photos | Disque local, upload avant sauvegarde de fiche, lecture publique, absence de rétention automatique | Choix documenté comme proposé ; abandon de formulaire pouvant laisser un fichier orphelin. Définir sauvegarde, quota, rétention et stockage partagé seulement si plusieurs instances sont prévues |
| Signalements de bugs | File d'opérations par instance de repository ; fallback Windows supprimant la destination avant rename | Adapté au développement mono-processus ; pas de garantie d'atomicité multi-processus ni face à un arrêt entre suppression et rename |
| Disponibilité de la base | `checkConnection()` est lancé sans attente ; erreur seulement journalisée ; health retourne toujours ok | Choix liveness documenté. Ajouter une readiness distincte si elle sert de condition de déploiement ; pas de faux diagnostic de connectivité à partir du health actuel |
| Politique de mot de passe | Minimum serveur de 1 caractère, maximum 128 ; hash Argon2id ; aucun parcours d'inscription | Le minimum n'est pas une politique de provisioning robuste. Préciser la politique des futurs comptes de production avant modification de contrat |
| Transport et annulation | `HttpRequestOptions` accepte un signal, mais les hooks examinés ne le transmettent généralement pas ; retour HTTP typé via `payload as T` | Risque d'appels inutiles et de dérive de réponses, pas une absence de validation des entrées serveur. Introduire annulation/validation de réponse sur les frontières utiles et mesurées |

Les comportements suivants **ne sont pas des bugs** au regard du cadrage lu : effectif incluant les personnes inactives encore présentes dans une période ; désactivation différente des joueuses et du staff ; dates civiles Paris conservées même lors des changements d'heure ; corrections d'état en arrière pour ADMIN ; absence de blocage MATCH des dates hors saison ; conservation des routes `/dashboard/...`.

## 4. Architecture actuelle et lisibilité

### Flux et responsabilités

```text
main.tsx → RouterProvider → page → hook Query → service Web → httpClient
                                                                ↓ HTTP /api/v1
app.ts → router → authenticate → requireRoles → validateRequest → contrôleur
                                                               ↓
                                                      service métier
                                                               ↓
                                                      repository Prisma
                                                               ↓
                                                PostgreSQL + contraintes SQL
```

`packages/shared` fournit les schémas d'entrée, contrats HTTP, constantes et utilitaires purs ; il n'importe pas React, Express ou Prisma. Les propriétés TypeScript en camelCase sont adaptées aux tables/colonnes SQL par `@map`/`@@map`. Le client généré reste interne à l'API.

`LeagueSeason` représente une édition d'une ligue dans une saison globale. Participations et journées y sont rattachées ; les matchs dépendent de leur journée. Les affectations TeamPlayer/TeamStaffMember représentent des périodes historiques inclusives. Les contraintes d'exclusion arbitrent les chevauchements. Les réservations techniques des équipes sont dérivées par trigger des matchs actifs et ne constituent pas une seconde source métier modifiable depuis les repositories.

Les controllers produisent les DTO et les dates sérialisées. Player/Staff produisent aussi leurs DTO dans les services ; ce choix est cohérent localement mais constitue une frontière variable selon les domaines. Auth accède directement à Prisma et health ne dispose pas de repository ; ces petites exceptions ne justifient pas des couches supplémentaires.

Le navigateur conserve les données serveur dans TanStack Query, les formulaires surtout dans React Hook Form, et les interactions/quelques formulaires dans React. Les services HTTP sont centralisés. Les ressources du dashboard et leurs routes canoniques disposent d'un module commun ; les breadcrumbs respectent globalement liste → détail → modification. Les tests de navigation vérifient plusieurs accès directs et destinations explicites.

L'infrastructure externe se limite essentiellement à PostgreSQL, au système de fichiers et à Traefik/déploiement SSH dans les workflows examinés. Les images externes sont chargées par le navigateur, sans téléchargement serveur constaté. Il n'y a pas de client mail/paiement ou autre intégration applicative observée dans les parcours relus.

### Qualité observée

| Axe | Évaluation fondée sur le code |
| --- | --- |
| Typage/validation | TypeScript strict, lint avec analyse des types, schémas Zod stricts et schémas de formulaires adaptés. Quelques assertions restent nécessaires à la frontière des statuts SQL et du transport ; elles ne valident pas les réponses à l'exécution |
| Sécurité | JWT vérifié avec algorithme fixé, expiration requise, relecture utilisateur/rôle actif à chaque requête, droits serveur par route, erreurs génériques sans SQL et requêtes SQL paramétrées. Les gardes Web ne sont pas l'autorité de sécurité |
| Concurrence/historique | Bonne protection MATCH : verrou avant lecture, version conditionnelle, contraintes SQL et tests simultanés. Affectations protégées par verrou personne et exclusion SQL. Les traductions d'erreurs restent moins uniformes que les contraintes |
| Lisibilité | Découpage métier pertinent ; fichiers majoritairement de taille raisonnable. La densité de MATCH/Staff et des chaînes de schémas masquait cependant les étapes ; améliorations réalisées ci-dessous |
| Duplication | Formats de listes, DTO de dates, filtres d'URL et tables/carte mobile souvent répétés ; duplication locale lisible, mais risque de divergence comme les deux compteurs de matchs |
| Couplage | Hooks globaux et hooks de feature coexistent ; certaines permissions Staff réemploient des noms League/Player. Cela décrit une proximité de valeurs, pas nécessairement la même règle métier |
| Testabilité | Application importable sans ouvrir le serveur, repositories simulables, bases temporaires dédiées, tests de contrats et flux Web avec HTTP simulé. Absence d'E2E et de validation du rendu réel |

Un scan des **298 modules source TypeScript/TSX** a résolu 995 liens d'import/réexport locaux et Shared, sans cycle détecté. Ce scan inclut les imports de types ; il ne constitue pas une analyse complète de résolution Node, des dépendances externes ou de tous les imports dynamiques.

Les recherches n'ont pas trouvé de `as any`, d'appel SQL Unsafe ou de `dangerouslySetInnerHTML` dans les sources applicatives recherchées. Cette observation ne prouve pas l'absence de toute vulnérabilité. Certaines constantes générales de rôles et le schéma générique de pagination paraissent peu consommés ; des exports publics Shared et des composants de compatibilité ne doivent pas être supprimés sur ce seul constat.

### Refactorisations proposées séparément

| Proposition | Problème/bénéfice | Coût et risques |
| --- | --- | --- |
| Politique explicite de mutations et invalidations | Des caches de référentiels MATCH vivent sous `leagueKeys.all`/`teamKeys.all`, mais plusieurs mutations n'invalident que `lists()`. Cartographier les vues dépendantes réduit les données obsolètes | Moyen ; éviter de provoquer un rechargement de tous les écrans à chaque mutation. Ajouter des tests de cache ciblés avant extraction |
| Petite abstraction des erreurs de concurrence | Les services répètent les traductions avec des variations ; Season ne traite pas P2034 au même endroit que MATCH | Faible à moyen ; conserver les codes métier distincts et les exceptions propres au domaine. Éviter un wrapper global qui transforme toutes les erreurs en conflit |
| Alignement progressif des DTO | La sérialisation est dans les contrôleurs pour plusieurs domaines et dans les services pour Player/Staff | Moyen ; bénéfice si les services ont plusieurs consommateurs. Aucun déplacement de fichiers nécessaire pour le seul style ; coordination des tests indispensable |
| Helpers limités pour les listes | Parsing URL et pagination répétés ; les contrats générique et métiers divergent déjà | Moyen à élevé si le contrat change. D'abord extraire les opérations purement internes réellement identiques ; garder les schémas métier explicites |
| Séparation de chargement des écrans publics/admin | Bundle principal mesuré à 706,53 kB | Faible à moyen ; tester les états de chargement, erreurs et navigation des routes lazy |

Une réorganisation en architecture hexagonale, un framework d'injection ou une couche de repository générique ne présente pas de bénéfice démontré suffisant pour cette taille de projet. Ils ne sont pas proposés dans cette passe.

## 5. Nomenclature

| Contexte | Convention à retenir | Observation |
| --- | --- | --- |
| Variables/fonctions | Anglais, camelCase, verbes décrivant l'action | Globalement respecté ; callbacks `v`, calcul `programming` et alias `utcDate` améliorés |
| Booléens | `isX`, `hasX`, `canX` selon état, présence ou droit | `isActive`, `isPublished`, `canDelete`, `hasProtectedDependencies` sont explicites ; `pending` reste compréhensible dans un composant local |
| Composants/types | PascalCase singulier ; hooks `useX` | Respecté dans les features ; `StaffMember`, `Player`, `LeagueSeason` différencient personne et édition |
| Fichiers API/services | `<domain>.<responsibility>.ts` | Différence légitime avec les composants `.tsx` PascalCase et utilitaires camelCase |
| Constantes/statuts | UPPER_SNAKE_CASE | Codes SQL et contrats préservés ; ne pas renommer `SCHEDULED`, `REGISTERED` ou les codes d'erreur |
| SQL/Prisma | SQL singulier snake_case ; modèles PascalCase ; propriétés camelCase | Mappings observés cohérents. GameMatch est un modèle existant, pas un motif de renommage de table |
| Routes | API versionnée, ressources pluriel kebab-case, paramètres `...Id` | Routes `/dashboard/...` préservées ; `/admin/matches` est une particularité réelle de l'API MATCH |

| Langues | Anglais pour la technique, français pour textes utilisateur | Pas de traduction des codes/API. Les messages d'erreur français/anglais sont des textes externes et ont été conservés |

`CREATE_LEAGUE_ROLES`/`VIEW_LEAGUE_ROLES` côté Web et `TEAM_CREATE_ROLES`/`SEASON_VIEW_ROLES` utilisent des ordres de mots différents sans empêcher la compréhension. Le réemploi de `VIEW_LEAGUE_ROLES` ou `PLAYER_WRITE_ROLES` pour d'autres ressources mérite un alignement progressif : les valeurs peuvent être identiques aujourd'hui sans que les règles restent liées demain. Un alignement des noms de permissions doit séparer les identités métier des simples aliases de valeurs.

Les écarts de pagination (`limit=25`/`sort` génériques contre `pageSize=20`/`sortBy`/`sortOrder` métier), de routes admin et d'outillage Git sont déjà documentés. `.validate-branch-namerc` accepte tout, commitlint utilise Conventional Commits ; les formats demandés dans AGENTS ne sont donc pas assurés automatiquement. Aucun contrat, outil Git ou route n'a été uniformisé silencieusement.

Renommer `pictureUrl`, `leftAt`, `GameMatch`, une table, un code d'erreur, un export public Shared ou un chemin HTTP demanderait une étude de compatibilité ; une modification SQL impliquerait une migration. Aucun renommage de ce type n'a été appliqué.
